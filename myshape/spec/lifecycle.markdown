# 每一種卡的生命週期

這一頁是規範：看板上每一種需要有人動的卡有哪些狀態、每個狀態誰負責、期限到了怎樣。程式在 `myshape/src/lifecycle.ts`（狀態表 `LIFECYCLE` 與推導）、`lifecycle-settings.ts`（期限與預設值）、`stalls.ts`（「沒人接」與「沒人處理的議題」兩種卡）；改這一頁就要在同一個 PR 改那些檔。

看板保證的是一句話（不變式 I）：看板知道的每一張需要動作的卡，任何時刻都恰好在它那種卡的一個狀態；不是終止狀態時它有負責人，負責人是 aggregator 時有期限，期限到了一定到船長面前。看板強制的是形狀，不是內容：它不派工、不答也不關待決事項、不改 aggregator 的資料、不自動封存議題、不關要你動手的項目、也從不提議關閉任何東西。

## 1. 負責人與兩段期限

| 負責人 | 意思 | 看板保證的 |
| --- | --- | --- |
| 船長 | 下一步是頁面上的一個按鈕 | 卡在展開可見的地方：決定佇列（正在顯示，或算在「還有 N 個決定排隊」裡）、首頁的「要你動手」、橫幅、左側欄 |
| aggregator | 下一步是它的指令或它自己的動作 | 有提醒期限與交給船長的期限，起算時間存在 `data/myshape/lifecycle.json`，重啟不歸零 |
| 看板 | 看板自己有界的一步（讀取、重試、輪到下一個） | 那一步有上限 |
| 時間 | 下一步是一個存下的時刻，或另一張看板看得到、自己有負責人的卡結束 | 時刻存在看板的檔裡 |

每個 aggregator 負責的狀態有兩個期限：提醒（給 aggregator）與交給船長。期限是船長的設定（第 5 節）。

提醒期限一到，看板提醒 aggregator 一次（`stall.nudge`，固定的句子與固定的 id 在 [contracts](contracts.markdown) 第 7.1 節）：同一次判斷到期的卡合成一則；讀來的卡只在它的 home 最後一次讀取是好的時才提醒；已經過了交給船長期限的卡不提醒，直接交給船長。提醒過了記在那張卡的計時上（第 6 節），存好了才交出，所以同一段卡住只提醒一次，重啟之後也一樣；狀態一變重新計時，之後到期就再提醒一次。提醒不會讓卡離開它的狀態。

起算時間是看板第一次看到那張卡在那個狀態的時刻；狀態一變（或 agent 的狀態、說明、最後一筆帳本事件一變）就從那一刻重新算。上線那一刻起每張卡重新算，所以上線當下沒有任何卡已經逾期。

看不清的狀態（T5、D10、Q10、A8）保留原來的計時，不重算。看板服務啟動之後、根 home 第一次讀好之前，看板不判斷也不存任何計時。
讀來的卡只在它的 home 最後一次讀取是好的（有回報、沒有過期）時才交給船長。沒有頁面時看板自己慢慢讀（每個 home 上一次讀完後 15 分鐘，遠端的 1 小時，[contracts](contracts.markdown) 第 10 節），那時過期的門檻是這個間隔的兩倍，所以沒有人看頁面時提醒與交給船長照常；那個 home 讀不好的期間計時照走，等讀好了再判斷。靠「不見了」才成立的事（卡離開某個狀態、議題變成沒有工作）只在那個 home 一次好的讀取之後才算；讀取失敗、exit 4、版本不對、不是合法的回報都不算。已經交給船長的卡，home 之後讀不好，仍留在船長面前。

## 2. 每一種卡的狀態

「第一個符合的」是由上往下判斷，程式就是照這個順序的規則表。

### 2.1 議題（看板存的）

| 狀態 | 條件（第一個符合的） | 負責人 | 期限 |
| --- | --- | --- | --- |
| T8 已封存 | 在封存檔 | 終止（可以重開） | — |
| T10 位置壞了 | 不在任何佇列 | 看板：啟動時放到「一般」最後，記一筆 `topic.moved`；佇列裡不是議題的 id 拿掉，也記一筆 | — |
| T3 提議關閉 | 有 aggregator 的 `close_proposal` | 船長 | 在決定佇列裡 |
| T7 排程中 | 在「待辦」、有排程 | 時間（排程） | — |
| T6 待辦 | 在「待辦」、沒有排程 | 船長 | 不計時（決定 3） |
| T4 先不關到某天 | 在「高」或「一般」，船長按了「先不關，到某天」，日期還沒到 | 時間 | 那個日期（`lifecycle.json` 的 `kept`），到了重新判斷 |
| T1 有工作 | 至少一張開著的卡在它底下 | 時間（那些卡各自的負責人） | — |
| T5 看不清 | 沒有開著的卡，但根 home 還沒讀好，或最後一次在某個 home 看到它的卡、而那個 home 現在讀不好 | 看板（等讀取） | 不會變成 T2；計時照原來的 |

開著的卡：還沒結束的 agent、排隊中的項目、任何待決事項、worker 提問、要你動手的項目、排程、還沒送完或沒送到的寫入。

T2 過了期限，看板在船長面前放一張「沒人處理的議題」（第 3 節）。aggregator 的 `close-propose` 照舊是 T3 的「提議關閉」，和看板的卡分開；看板從不寫 `close_proposal`。

`aged` 的待決事項照 `live` 排，卡上標「已放超過 14 天」；`dated` 的日期到了也照 `live` 排，標「延到 …，日期到了」。D9 的卡照原文寫出讀到的字，照常可以作答。D5 過了期限，那個決定本身進決定佇列，照常可以作答，卡上寫「它等的 <id> 看板找不到」。

終止：有 `hold.answered` 或 `hold.closed` 的已關；上一次好的讀取還開著、這一次好的讀取既不開著也不在 `closed_holds[]` 的不見了，看板寫一筆 `hold.vanished`（只對回報已關待決事項的 home，`closed_cursor` 有給的；其他 home 分不出關掉與不見）。

### 2.3 排隊中的項目（讀來的）

| 狀態 | 條件（第一個符合的） | 負責人 | 期限 |
| --- | --- | --- | --- |
| Q10 看不清 | 那個 home 讀不好 | 看板 | — |
| Q9 讀不懂 | `hold_until` 或 `turn` 的值不合法（[contracts](contracts.markdown) C14） | aggregator | Q9 |
| Q2 等船長決定 | `captain` 是 true | 船長（經它的待決事項） | — |
| Q4 封存議題底下 | 它的議題已封存 | aggregator | Q4 |
| Q3 跟著議題停 | 它的議題在「待辦」 | 船長（經那個議題） | 不計時 |
| Q7 等其他工作 | `blockers` 都是看板看得到的開著的卡，不繞圈 | 時間 | — |
| Q8 等看不到的工作 | `blockers` 有看不到的或繞圈 | aggregator | Q8 |
| Q6 延到某天 | `hold_until` 那一天（或那一刻）再過一天之前 | 時間 | — |
| Q1 排到就做 | `turn` 是 true | aggregator | Q1 |
| Q5 沒人接 | 有 `hold` 的文字 | aggregator | Q5 |
| Q1 排到就做 | 其他 | aggregator | Q1 |

看板不讀 `hold` 的文字、不認任何 aggregator 的 hold kind；`hold_until` 與 `turn` 是 aggregator 交過來的說法，沒有時照今天推導。日期過了一天還在、日期也沒改，日期就不再解釋這個等待：有 `hold` 的是 Q5，沒有的是 Q1。議題移到「待辦」時底下的項目是 Q3、不計時；移回「高」或「一般」時從那一刻重新計時。移動議題只改看板自己的佇列與子卡的負責人和計時，派不派、停不停已在跑的 agent 都是 aggregator 的事。

**沒有議題**（NT）是旗標，和上面的狀態並存：沒有議題的排隊項目與還在跑的 agent，aggregator 負責補標記，期限 NT。

## 3. 交給船長：兩種看板的卡

期限一到，看板只把卡放到船長面前，不替任何人做決定。落點：

- T2：「沒人處理的議題」。卡上一句固定的話：「這個議題 <期限> 沒有任何工作，<aggregator 的名稱> 也沒處理」。按鈕：〔關閉並封存〕（就是封存）、〔先不關，到 <日期>〕（預設 14 天，最多 90 天，存成 T4）、〔移到待辦〕（就是移動）。議題離開 T2（有了工作、移到待辦、封存）卡就不需要了。
- D5：那個決定本身進決定佇列。
- 其他（D8、D9、Q1、Q4、Q5、Q8、Q9、NT、A1–A6、W1、O3、S3、S6）：它議題的「沒人接」卡；沒有議題的另有一張。

「沒人接」卡的狀態：

| 狀態 | 條件 | 負責人 | 期限 |
| --- | --- | --- | --- |
| N1 已過提醒 | 有成員過了提醒期限、還沒有過了交給船長的期限 | aggregator | 成員各自的 |
| N2 交給船長 | 有成員過了交給船長的期限 | 船長（在決定佇列裡） | — |
| N3 請它處理 | 船長按了〔請 <aggregator> 處理〕，還沒過 N3 的期限，而且成員都是那時列出的 | aggregator | N3（第 5 節，預設 1 天）；過了回到 N2，卡上寫「已退回過一次」，不能再按 |
| N4 延到某天 | 船長按了〔延到 <日期>〕，日期還沒到，而且成員都是那時列出的 | 時間 | 船長選的日期，最多 90 天；之後新冒出來的成員照樣交給船長 |
| 已不需要 | 沒有成員過了期限 | 終止 | — |

一張卡同時有兩個逾期的原因（例如一筆停著又沒有議題的項目）只列一行，兩個原因寫在一起。「沒人接」卡的按鈕：〔延到 <日期>〕、〔移到待辦〕（沒有議題的那張沒有）、〔請 <aggregator> 處理〕（一張卡只能按一次；沒有議題的那張沒有，因為訊息一定在一個議題底下）；成員是排程的另有〔恢復排程〕（S3）或〔暫停排程〕（S6），沒有議題的排隊項目與 agent 另有既有的歸併選單（〔歸到…〕、〔歸併到…〕，送 `tag`）。卡上沒有「關閉並封存」，也沒有關掉要你動手項目的按鈕。〔請 <aggregator> 處理〕送一則固定句子的 `message`（[contracts](contracts.markdown) 第 7.1 節），列出那時的成員。

兩種卡存在 `lifecycle.json`（第 6 節）；出現時寫一筆 `stall.raised`，不需要了寫一筆 `stall.settled`（`outcome` 是 `idle` 或 `stall`），船長的〔先不關〕、〔延到〕與〔請 <aggregator> 處理〕寫 `lifecycle.answered`（`outcome` 是 `kept`、`deferred` 或 `asked`），`by` 照 contracts 第 3.3 節。

## 4. 一條決定佇列

所有要船長決定的卡排同一條佇列，一次一個（決定 4 選 A）：

1. aggregator 的待決事項（含 `aged`、日期到了的 `dated` 與過了期限的 D5），照第三段的順序；
2. aggregator 的提議關閉；
3. 看板的「沒人處理的議題」；
4. 看板的「沒人接」卡（N2）。

同一種之內照議題的佇列與位置，再照時間。上限：aggregator 宣告了 `decisions_at_once` 時，四種合起來就是那麼多；沒有宣告時待決事項照舊全部顯示，後三種受看板自己的上限 1 管。其他的摺成「還有 N 個決定排隊，輪到時才顯示」。

看板這個程序看過在排隊、現在輪到的卡，送一則 `decision.front`，固定的句子只寫是誰的卡、在哪個議題與還有幾個排隊，不寫問題、原因或成員（[contracts](contracts.markdown) 第 7.1 節）。

順序與上限的常數在 `lifecycle-settings.ts` 的 `TURN_ORDER` 與 `BOARD_CAP`。

## 5. 期限的設定

船長在首頁的「期限設定」調，只在頁面上（`lifecycle-settings`，socket 收到就拒絕），每一筆改動寫一筆 `lifecycle.settings_changed`，帶改前改後。每一項是 `{remind, raise}`：分鐘（S6 是連續第幾場）；兩個都是整數，提醒不能晚於交給船長，交給船長至少 1，分鐘最多 90 天（S6 最多 10 場）；任何一項不合法就都不改。讀到沒有或不合法的值用預設。
N3（船長按了〔請 <aggregator> 處理〕之後，aggregator 有多久）只有 `{raise}`：提醒不適用，因為船長按的那一下就是交給 aggregator 的那句話；頁面上那一列的提醒寫「不適用」，帶 `remind` 的改動拒絕。

預設（決定 2 選 A）：

| 狀態 | 提醒 | 交給船長 |
| --- | --- | --- |
| T2、D5、Q4、Q5、Q8、NT、A2、A5、W1、O3 | 1 天 | 3 天 |
| D8、D9、Q9、A6 | 立刻 | 1 天 |
| Q1、A1、S3 | 3 天 | 7 天 |
| A3 | 15 分鐘 | 2 小時 |
| A4 | 1 小時 | 1 天 |
| S6 | 連續第 3 場 | 連續第 5 場 |
| N3 | 不適用 | 1 天 |

另外的預設是常數，不是期限（第 2.15 節不列）：先不關與延到預設 14 天、最多 90 天（決定 3），沒有宣告上限時看板自己的上限 1、佇列的順序（決定 4），與延到某天的排隊項目過了日期之後還算延到的 1 天（`DATE_GRACE_MINUTES`，Q6 是時間負責的狀態）。

```json
                           "deferred": { "until": "…", "members": ["queued\tmain\tfoo"] },
                           "asked": { "at": "…", "members": ["queued\tmain\tfoo"] } } },
  "idle": { "t2": "2026-11-30T08:00:00.000Z" },
  "outbox": []
}
```

- 卡的鍵是種類、home（讀來的卡）與 id，用 tab 分開；沒有議題的旗標再加 `\tNT`。
- `clocks`（每張計時中的卡何時進入那個狀態，`reminded` 是這一段有沒有提醒過 aggregator）、`homes`（每個議題最後在哪些 home 看到它的卡）、`stalls` 與 `idle`（兩種看板的卡）是看板的記憶：每次看完（每次讀好一個 home 之後，與每 30 秒的時鐘）經 `commitChange` 存，記憶本身沒有變化就不寫。只改記憶、沒有轉移的那一次不帶紀錄，也不換掉檔裡的 `outbox`；這是唯一可以沒有紀錄的改動，型別只讓它換掉這四個欄位。
- `settings`、`kept`、N4 的 `deferred` 與 N3 的 `asked` 只由船長在頁面上改，每一次都帶紀錄；`asked` 跟著卡留到它不需要為止，所以一張卡只能請 aggregator 處理一次。〔先不關，到某天〕對提議關閉是議題的改動，`lifecycle.json` 先寫、`topics.json`（帶紀錄）後寫：中途當掉時提議還在，再按一次就好。
- 讀的一方略過不認得的欄位與不完整的項目；舊版看板不讀這個檔，退回再升上來時照檔裡的接著算。

## 7. 限制

- 看板服務沒在跑時什麼都不判斷；回來時照存下的計時接著算，逾期的照一次一個的上限排出。
- 沒有頁面時的讀取是慢的：讀來的卡的起算是看板第一次讀到它的時刻，遠端的 home 最多晚約一小時。
- 還沒更新的 home 送不出 `hold_until` 與 `turn`：它的有日期或排到就做的等待在看板上是 Q5，期限照 Q5。
- 沒有議題的「沒人接」卡沒有〔請 <aggregator> 處理〕：`message` 一定在一個議題底下。
